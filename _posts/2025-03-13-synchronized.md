### 悲观锁

**1. 概念**  
悲观锁认为数据在并发访问时很可能会出现冲突，所以在每次操作前都先加锁，确保同一时刻只有一个线程能够访问资源。也就是说，假设最坏情况，始终存在冲突，因此采取严格的加锁措施。

**2. 实现方式**  
- **synchronized 关键字**：这是 Java 内置的实现方式，可以用在方法或代码块上。例如：
  ```java
    public class Counter {
        private int count = 0;

        // 使用 synchronized 保证同一时刻只有一个线程进入该方法
        public synchronized void increment() {
            count++;
        }

        public synchronized int getCount() {
            return count;
        }
    }

  ```
- **显示锁（Lock 接口）**：如 `ReentrantLock`，提供了更多的灵活性和功能，例如超时锁、可中断锁等。
  ```java
  ReentrantLock lock = new ReentrantLock();
  lock.lock();
  try {
      // 修改共享资源的代码
  } finally {
      lock.unlock();
  }
  ```

**3. 特点与适用场景**  
- **优点**：数据安全性高，能够有效避免并发冲突。  
- **缺点**：加锁和解锁操作会带来性能开销；在冲突频繁时可能导致大量线程阻塞，降低系统吞吐量；不当使用还可能引起死锁。  
- **适用场景**：冲突较频繁、数据争用严重的场景，如对共享资源的写操作非常频繁时。

### 乐观锁

**1. 概念**  
乐观锁认为在大多数情况下并发冲突并不常见，因此在操作数据时不加锁，而是在更新时进行校验。通常会在数据中引入版本号或者时间戳，在提交更新前先验证数据是否被其他线程修改过。如果检测到冲突，则拒绝更新或者重试。

**2. 实现方式**  
- **CAS（Compare and Swap）机制**：Java 提供了原子类，如 `AtomicInteger`、`AtomicReference` 等，内部基于 CAS 实现无锁操作。
  ```java
  AtomicInteger atomicInt = new AtomicInteger(0);
  // 期望值为0时，将其更新为1
  boolean updated = atomicInt.compareAndSet(0, 1);
  ```
- **版本号机制**：在数据库或业务层中常见，每条记录都有一个版本号，更新时带上当前版本号，更新成功后版本号加一，如果版本号不匹配则表示数据已被修改，需要重试或提示冲突。

**3. 特点与适用场景**  
- **优点**：避免了锁的使用，减少了线程阻塞和上下文切换，性能更高，特别适合读多写少的场景。  
- **缺点**：在冲突发生时需要重试，可能会导致操作失败或性能下降；不适合并发冲突非常频繁的场景。  
- **适用场景**：数据写操作较少、冲突概率低的场景，如缓存更新、库存扣减（乐观锁方式通常配合重试机制）等。

---

### 总结

- **悲观锁**：  
  - **思路**：认为会发生冲突，因此每次操作前加锁。  
  - **实现**：`synchronized`、`ReentrantLock` 等。  
  - **适用场景**：冲突频繁、写操作较多的场景。

- **乐观锁**：  
  - **思路**：认为冲突少，因此不加锁，而是在更新时进行校验。  
  - **实现**：CAS 机制、版本号控制等。  
  - **适用场景**：读多写少、冲突概率低的场景。

## 🔖 一、概念区别（含义不同）

- **`synchronized`**：
  - 是Java内置的 **锁机制**，用于实现线程的同步访问。
  - 能够保证**原子性**（多个操作看起来像一个整体）和**可见性**（线程间能看到最新数据）。

- **`volatile`**：
  - 是一种轻量级的同步机制，只能保证变量的**可见性** 和 **禁止指令重排序**。
  - 无法保证**原子性**（不能保证复合操作如`++`、`--`的安全）。

---

## 🔖 二、作用机制上的区别

| 特性         | synchronized                 | volatile                     |
|--------------|------------------------------|------------------------------|
| 可见性       | ✅ 能保证可见性                 | ✅ 能保证可见性                  |
| 原子性       | ✅ 能保证原子性                 | ❌ 无法保证原子性                |
| 指令重排序   | ✅ 可禁止（通过锁）             | ✅ 禁止重排序（轻量级内存屏障） |
| 是否加锁     | ✅ 加锁（重量级）               | ❌ 不加锁                      |
| 性能开销     | 较大                         | 很小                         |

---

## 🔖 三、适用场景的区别（重点掌握）

### ① 什么时候用 `synchronized`？

- 当需要保证线程间的互斥访问（例如修改共享变量的复合操作）。
- 当需要保证多个操作整体执行时（保证原子性）。

例如：

```java
class Counter {
    int count = 0;

    synchronized void increment() {
        count++; // 保证原子性
    }
}
```

---

### ② 什么时候用 `volatile`？

- 当只需要保证**变量的可见性**时（例如状态标记）。
- 当只有**单一操作的变量读写**，不涉及复合操作（如 i++）。

例如：

```java
volatile boolean flag = false;

// 线程1
void writer() {
    flag = true;
}

// 线程2
void reader() {
    while (!flag) {
        // 等待flag变为true
    }
}
```

---

## 🔖 四、为什么 `volatile` 不能保证原子性？

举例说明：

```java
volatile int num = 0;

void increment() {
    num++; // 看似简单，但实际是三个操作：
           // 1. 读取num
           // 2. num+1
           // 3. 写回num
}
```

- 虽然`volatile`保证了变量的**读写可见性**，但 `num++` 本身不是原子操作。
- 多个线程同时执行时，依然会产生竞争、线程安全问题。

要实现原子操作，必须使用`synchronized`或`AtomicInteger`等工具。

---

## 🔖 五、性能差异（开销区别）

- **synchronized**：
  - 重量级锁，获取和释放锁的开销较大。
  - Java 6+之后进行了大量优化（如偏向锁、轻量级锁），性能有所提高，但依然有一定开销。

- **volatile**：
  - 轻量级，不加锁。
  - 性能损耗极小。

> 所以，能用volatile解决的问题，**不推荐使用重量级的synchronized**。

---

## 🔖 七、经典面试题举例（自测理解）

- 问：`volatile int a = 0; a++`线程安全吗？为什么？
  - **回答：**不安全，因为`a++`不是原子操作，只用`volatile`不能解决这个问题，需`synchronized`或`AtomicInteger`。

- 问：什么时候该使用`volatile`而不是`synchronized`？
  - **回答：**只有简单赋值操作，且只需保证线程可见性，无需保证原子性时，使用`volatile`更轻量高效。

---

## 🚀 总结一句话：

- **需要互斥+原子性**用`synchronized`；
- **只要可见性、禁止重排序**用`volatile`更轻量。
